# image-to-description のメモリ・ロック対策

この文書は人間向けの運用手順です。デプロイや本番データ修復を許可するものではなく、実行可否はルート `AGENTS.md` に従います。

## 実装した対策

- 画像本体を関数メモリへダウンロードせず、`gs://` URIをVertex AIへ渡す。
- 画像の最大20枚、合計100 MB、ファイル名順という既存制限を維持する。
- 処理ロックが15分以上更新されていない場合だけ期限切れ候補とする。
- 確認したGCS世代番号を `if_generation_match` に指定し、同じ世代のロックだけを削除する。
- 回収中に別処理がロックを更新した場合、その新しいロックは削除しない。
- 正常終了時も、現在の処理が取得した世代のロックだけを削除する。

`_SUCCESS.txt`、`_description.txt`、`_description_processing.lock` の名前とGCSイベント契約は変更しない。

## 推奨ランタイム設定

| 設定 | 値 | 理由 |
|---|---:|---|
| メモリ | 512 MiB | GCS URI方式で画像本体を保持せず、現行上限を維持して実測する |
| Concurrency | 1 | 同じインスタンスで複数商品が同時にメモリを使用することを防ぐ |
| Timeout | 540秒 | 15分のロック期限より短くし、実行中ロックを期限切れ扱いしない |

512 MiBで再検証し、メモリ超過が再発した場合だけ1 GiBへの増加を検討する。256 MiBへの縮小は、最大使用量へ十分な余裕があることを実測するまで行わない。

## デプロイ準備と実績

`scripts/prepare_deploy_image_to_description.ps1` は対象を固定し、次を行う。

1. `image-to-description` の未コミット差分がないことを確認する。
2. `python scripts/check.py` を実行する。
3. 対象、ソースコミット、メモリ、Concurrency、Timeout、完全なコマンドを表示する。
4. `-Execute` がなければ外部操作を行わず終了する。

2026-07-25に、PR #12のマージコミット `ad7edae` を `image-to-description` へデプロイした。稼働中Revisionは `image-to-description-00004-hub` で、メモリ512 MiB、Concurrency 1、Timeout 540秒、トリガーバケット `test-review-ui`、再試行無効を確認済みである。

デプロイ後の商品テストは未実施である。1商品canaryが成功してから10商品テストへ進み、メモリ不足、残存ロック、生成物の不足・重複がないことを確認する。GCS書き込み、`_SUCCESS.txt` 再投入、Gemini/Vertex AI呼び出しを伴う検証は、ルート `AGENTS.md` の事前確認と承認条件に従う。

## 期限切れロックからの復旧

通常のエラーでは `finally` によりロックを削除する。メモリ超過などでプロセスが強制終了した場合は、次のイベント処理時に期限切れ回収を試みる。

1. `_description.txt` が存在する商品は処理済みとして終了する。
2. ロック取得に失敗した場合、既存ロックの更新日時と世代番号を読み取る。
3. 15分未満なら実行中と判断し、回収しない。
4. 15分以上なら、読み取った世代番号を条件に削除する。
5. ロックをもう一度新規作成し、別処理が先に取得していた場合は処理を中止する。

Eventarcの再試行が無効、または再試行が終了している場合は、人間が対象商品だけの `_SUCCESS.txt` を新しいGCS世代として再投入する。画像を先に配置し、`_SUCCESS.txt` は最後に投入する。

本番ロックの手動削除や `_SUCCESS.txt` の再投入は本番データ修復に当たるため、Codexは実行しない。人間は対象商品、`_description.txt` の不存在、ロック世代、コピー元・コピー先を確認し、成功済み商品を対象から除外する。

## 確認項目

- 対象商品の `_description.txt` が生成される。
- 元の `_description_processing.lock` が残らない。
- `result.json`、`review_required.csv`、`mercari.csv`、`_DONE.txt` が商品数分生成される。
- Review UIの商品数が期待件数と一致する。
- 成功済み商品に重複行や上書きが発生しない。
- メモリ超過ログが再発しない。
